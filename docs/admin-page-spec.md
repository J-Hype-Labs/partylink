# 관리자 페이지 명세 (초안 v0.1)

- 작성일: 2026-11-09
- 상태: **초안 — 아래 "11. 결정이 필요한 항목"이 정해지면 v1.0으로 확정**
- 대상: `J-Hype-Labs/party-connect-mvp`의 관리자 화면 + `J-Hype-Labs/partylink`의 관리자 API
- 요청 배경: 동료의 관리자 페이지 개발 요청. 현재 사이트의 관리자 화면은 껍데기이고, 서버 쪽 API는 이미 있습니다.

---

## 1. 한 줄 요약

> 관리자가 **카카오로 로그인**하고, 서버가 `admins` 테이블로 권한을 확인한 뒤, **파티 등록·신청 선정/반려·방문 후 승인·노쇼·적립금·게스트 차단**을 화면에서 처리한다.
> 기존 데모 관리자 모달(하드코딩 비밀번호)은 대체 대상이다.

## 2. 현재 상태 (조사 결과)

### 2.1 사이트 (`party-connect-mvp`, `main` 기준)

| 항목 | 현재 |
|---|---|
| 관리자 진입 | 푸터의 "관리자" → `index.html` 안의 모달 (`isAdminOpen`) |
| 인증 | 프런트에 하드코딩된 비밀번호 비교 (`ADMIN_PASSWORD`). 정적 Pages에서는 누구나 읽을 수 있어 **운영 사용 불가** |
| 탭 | `dashboard / parties / applications / reviews / stats` 5개가 있으나 내용은 "데모 구현 영역" 문구뿐 |
| 데이터 | 파티·후기 폼 상태만 있고 `localStorage` 기반. DB와 연결 없음 |
| 테스트 | 모달이 열리는지만 확인. CRUD는 미검증 (`SPECIFICATION.md`, `README.md`에 "미검증"으로 명시) |
| 규모 | `index.html` 1,808줄 한 파일에 메인 페이지 전체가 들어 있음 |

기존 문서들(`AUTH_IMPLEMENTATION_SPEC.md` AUTH-05, `UI_UX_DECISION_RECORD.md`, PR 7)이 모두 같은 결론입니다: **비밀번호를 환경변수로 옮기는 것은 해결책이 아니고, 서버 측 권한 검증으로 가야 한다.**

### 2.2 서버 (`partylink`, `main` 기준 — 이미 Supabase에 배포됨)

`/functions/v1/partylink-api/admin/...` (카카오 로그인 토큰 + `admins` 등록 필수, 미로그인 401 / 비관리자 403)

| 영역 | 있는 것 |
|---|---|
| 권한 | `GET /admin/me` |
| 점포 | 목록(+적립금 잔액), 적립금 원장, 충전, 환불 |
| 파티 | 목록(모든 상태, 선정/신청 인원), 등록, 수정(상태 변경 포함) |
| 신청 | 목록(게스트 연락처·미션 URL 포함), 선정, 반려, 최종 승인, 노쇼 |
| 게스트 | 목록(`?blocked=1`), 수동 차단/해제 |

관리자 등록은 `admins` 테이블에 SQL로만 합니다. 현재 1명(대표) 등록돼 있습니다.

## 3. 작업 범위 분리 (협업자와 겹치지 않기)

협업자(`6Soo` + 자동 에이전트)는 지금 **E2E 테스트 안정화, 인증 모듈(`js/auth-*.js`), 문서, 메인 페이지 UI**를 건드리고 있습니다. `main`의 CI가 아직 빨간 상태입니다.

| 영역 | 담당 | 관리자 작업에서의 규칙 |
|---|---|---|
| `tests/comprehensive.spec.js`, `tests/user-journey-*.spec.js` | 협업자 | **수정 금지.** 관리자 테스트는 새 파일로 분리 |
| `js/auth-client.js`, `auth-service.js`, `auth-ui.js`, `auth/callback/` | 협업자 | **읽기만.** 필요한 기능은 요청하거나 읽기 전용으로 재사용 |
| `index.html` (메인 페이지) | 협업자 | 관리자 진입 링크 **한 줄 교체**만 허용. 큰 수정 금지 |
| `party-connect/index.html` | 협업자 | 건드리지 않음 |
| `README.md`, `SPECIFICATION.md`, 기존 `docs/` | 협업자 | 건드리지 않음. 관리자 문서는 새 파일로 |
| **`admin/index.html` + `js/admin-*.js`** (신규) | **관리자 작업** | 새 디렉터리. 충돌 가능성 없음 |
| `tests/admin-*.spec.js` (신규) | 관리자 작업 | 새 파일. 외부 서버 호출은 모두 mock |
| `partylink` 저장소 `supabase/` | 관리자 작업 | API 갭 보완 (6장) |

**원칙:** 관리자 화면은 메인 `index.html` 안의 모달을 고치지 않고 **별도 페이지(`/admin/`)** 로 만듭니다. 그러면 파일이 겹치지 않고, 메인 페이지 CI 실패가 관리자 작업을 막지 않습니다. 기존 모달 제거는 관리자 페이지가 안정된 뒤 마지막에 합니다.

## 4. 화면 구성

모바일 우선, 데스크톱에서는 좌측 내비게이션. 한 화면에 한 가지 일만 하게 합니다.

| # | 화면 | 목적 | 핵심 동작 |
|---|---|---|---|
| A0 | 로그인/가드 | 접근 통제 | 카카오 로그인 → `GET /admin/me` 200이면 진입, 401이면 로그인 안내, 403이면 "권한 없음" |
| A1 | 대시보드 | 오늘 할 일 | 선정 대기 신청 수, 오늘/이번 주 파티, 적립금 부족 점포, 차단된 게스트. 각 카드는 해당 목록으로 이동 |
| A2 | 파티 | 등록·수정 | 목록(상태 필터) / 등록·수정 폼 / 상태 변경(DRAFT → OPEN → CLOSED …) |
| A3 | 신청 | 선정 업무의 중심 | 파티별·상태별 목록, 게스트 정보, 선정/반려(사유)/최종 승인/노쇼 버튼 |
| A4 | 점포·적립금 | 돈 관련 | 점포 목록과 잔액, 원장, 충전(입금자명), 환불 |
| A5 | 게스트 | 제재 관리 | 목록, 노쇼·벌점, 차단/해제 |
| A6 | 통계 | 현황 보기 | (결정 필요: 11장 Q3) |
| A7 | 후기 | 후기 관리 | (결정 필요: 11장 Q2 — 현재 DB에 후기 테이블 없음) |

### 4.1 신청 상태와 버튼 (A3)

```
APPLIED ──선정──▶ APPROVED ──방문 인증──▶ VISITED ──미션 제출──▶ MISSION_SUBMITTED ──최종 승인──▶ COMPLETED
   │                  │
   └─반려─▶ REJECTED   └─노쇼─▶ NOSHOW        (게스트 취소: CANCELLED)
```

| 현재 상태 | 관리자 버튼 | API |
|---|---|---|
| APPLIED | 선정 / 반려 | `POST /admin/applications/:id/approve` / `.../reject` |
| APPROVED | 노쇼 | `.../noshow` |
| MISSION_SUBMITTED | 최종 승인 (수수료 차감) | `.../complete` |
| 그 외 | 버튼 없음, 상태만 표시 | — |

- 최종 승인은 **점포 적립금에서 수수료를 차감**하므로 확인 대화상자에 금액과 점포명을 보여 줍니다. 잔액이 부족하면 서버가 402를 줍니다.
- 반려는 사유 입력(선택, 500자)을 받습니다.
- 모든 버튼은 요청 중 비활성화하고, 같은 신청을 중복 제출하지 못하게 합니다.

## 5. 인증·권한

1. 관리자 페이지는 메인 사이트와 **같은 Supabase 세션**(카카오 로그인)을 재사용합니다. 별도 비밀번호는 없습니다.
2. 진입 시 `GET /admin/me`로 서버에 확인합니다. **클라이언트가 가진 `role` 같은 값은 신뢰하지 않습니다.**
3. 모든 `/admin/*` 호출에 `Authorization: Bearer <access_token>`을 붙입니다. 토큰이 만료되면 한 번 갱신 후 재시도하고, 그래도 401이면 로그인 화면으로 보냅니다.
4. 브라우저에는 Supabase URL과 publishable key만 둡니다. `service_role`, 카카오 Client Secret, 관리자 비밀번호는 절대 넣지 않습니다.
5. 화면에서 버튼을 숨기는 것은 편의일 뿐이고, 권한은 **서버가 매 요청마다** 확인합니다.
6. 관리자 추가/삭제는 이 범위에서 UI로 만들지 않고 SQL로 합니다 (11장 Q5).

## 6. API 매핑과 갭

### 6.1 그대로 쓸 수 있는 것
2.2의 표 전부. 응답 필드는 `docs/party-connect-integration.md`의 "관리자 API" 절을 따릅니다.

### 6.2 화면에 필요하지만 아직 없는 것

| # | 필요 | 이유 | 제안 |
|---|---|---|---|
| G1 | 점포 등록·수정 | 파티를 등록하려면 점포가 먼저 있어야 함. 지금은 SQL로만 가능 | `POST /admin/stores`, `PATCH /admin/stores/:id` |
| G2 | 대시보드 집계 | 카드 숫자를 위해 목록을 전부 받아 세는 것은 낭비 | `GET /admin/summary` (선정 대기 수, 이번 주 파티 수, 잔액 부족 점포 수, 차단 게스트 수) |
| G3 | 파티 삭제/취소 | 잘못 만든 파티 처리. 지금은 `status`를 `CANCELLED`로 바꾸는 것만 가능 | 삭제는 만들지 않고 `CANCELLED` 사용. 화면에서 "취소"로 표기 |
| G4 | 방문 인증 대행 | 점주 앱이 없으므로 관리자가 코드를 대신 확인해야 할 수 있음 | `POST /admin/applications/:id/verify-visit {code}` (Q4에 따라) |
| G5 | 후기 | 데모 UI에는 후기 관리가 있으나 DB에 테이블이 없음 | Q2 결정 후 |
| G6 | 감사 로그 | 누가 선정/승인/환불했는지 | 우선 `deposit_histories.created_by`(적립금 변동의 처리자)만 사용. 별도 로그는 후속 |

### 6.3 데모 UI와 DB의 모델 차이 (이관 시 주의)

데모의 파티는 `region / days[] / venue / address / recruit` 등을 갖고, DB의 파티(`party_slots`)는 `starts_at / ends_at / recruit_deadline / capacity`와 점포(`stores`)를 갖습니다.

| 데모 필드 | DB |
|---|---|
| `region`, `venue`, `address` | 점포(`stores.region / name / address`)에서 옴 |
| `days: ["금","토"]` (반복 요일) | **없음.** DB는 특정 일시의 1회성 파티. 반복 파티는 날짜별로 여러 개 등록 |
| `recruit` | `capacity` |
| `badges / images / isFeatured / category` | 동일 이름으로 있음 (`20261106…` 마이그레이션) |

이 차이 때문에 **관리자 페이지의 파티 폼은 데모 폼을 복사하지 않고 DB 모델 기준으로 새로 설계**합니다. 사용자 화면의 "요일 필터"가 `days`에 의존하는 문제는 이 작업 범위가 아니라, 협업자와 따로 정해야 합니다 (Q6).

## 7. 비기능 요구사항

- **모바일 우선**, 최소 360px 폭에서 가로 스크롤 없음. 표는 카드형으로 전환.
- 모든 버튼·입력에 라벨, 키보드 조작 가능, 대화상자는 포커스 가둠(`role="dialog"`).
- 서버 오류 메시지(`{code, message}`)를 **그대로 화면에 표시**합니다. 서버가 한국어 문장을 줍니다.
- 개인정보(연락처 등)는 화면에는 보이되 로그·URL·`localStorage`에 남기지 않습니다.
- 빈 상태, 로딩, 실패 상태를 화면마다 만듭니다.
- 외부 라이브러리는 기존 사이트와 같은 방식(CDN, 버전 고정)만 사용합니다.

## 8. 테스트 계획

- **새 파일** `tests/admin-*.spec.js`. 기존 `comprehensive.spec.js`는 건드리지 않습니다.
- 실제 Supabase를 호출하지 않고 `page.route`로 `/admin/*`를 mock 합니다 (기존 라이브 fixture와 같은 방식).
- 필수 시나리오:
  1. 비로그인 → 로그인 안내
  2. 로그인했지만 403 → "권한 없음"
  3. 관리자 → 대시보드 표시
  4. 신청 선정/반려/최종 승인/노쇼 각 성공과 오류(402, 409, 410)
  5. 파티 등록 검증 오류, 상태 변경
  6. 충전/환불, 잔액 부족
  7. 게스트 차단/해제
- 서버 쪽은 기존 Deno 테스트(`handler_test.ts`)에 G1~G4 추가분을 더합니다.
- 협업자의 CI(E2E)가 안정되기 전까지는 **관리자 테스트를 별도 spec으로 두고 로컬/별도 실행**하는 것을 허용합니다.

## 12. 위험

- **`main` CI가 계속 빨간 상태**입니다. 병합 판단은 협업자의 안정화 이후로 미루고, 관리자 코드는 신규 파일로 두어 영향을 줄입니다.
- 관리자 API는 점주 대신 처리하는 강한 권한입니다. 최종 승인·환불은 되돌릴 수 없는 돈 관련 동작이라 확인 대화상자를 필수로 하고, 서버의 원장은 수정할 수 없는(append-only) 구조라는 점을 화면 문구에도 반영합니다.
- 현재 Edge Function은 대시보드에 단일 파일로 붙여 넣는 방식으로 배포합니다. 서버 갭을 보완할 때마다 번들링과 재배포가 필요하니, Supabase CLI 배포로 옮기는 것을 권장합니다.
- `SUPABASE_SERVICE_ROLE_KEY`(레거시 키)는 2027년 초에 종료되므로 그 전에 새 시크릿 키로 이전해야 합니다.
